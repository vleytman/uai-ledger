## 1. Вывод и границы

**Выбор владельца от 25.09.2026:** для Gemini первым этапом подготовить поддержку **Google Cloud Standard PayGo**, предусмотрев последующее подключение **Cloud Priority PayGo**. Standard уже является режимом pay-as-you-go; под последующим PayGo в этом решении понимается Priority. Сейчас фиксируются требования, реализация и включение платных маршрутов не поручены. Состав первого этапа приведён в разделе 13.

UAI можно расширить для Cerebras, Groq, Kie.ai и Google Cloud на существующей архитектуре. Общие очереди, учёт попыток, резервы, версии тарифов и выдача результатов сохраняются. Потребуются новые адаптеры и конфигурации, уточнение возможностей моделей, оценщики входа и отдельная обработка расходов посредников.

Под «картинками» в основном объёме понимается анализ изображений языковой моделью. Генерация и редактирование изображений, embeddings, видео, realtime, аудио и выполнение встроенных платных инструментов поставщика не входят в этот объём.

В этом исследовании не выполнялись платные генерации, не менялись подключения, тарифы в БД или рабочие маршруты. Состояние реализации проверено по текущей рабочей копии, включая незакоммиченные изменения. Производственная конфигурация и активные модели в БД не проверялись.

## 2. Что считать подтверждённым

- **Есть в коде**: механизм найден в рабочей копии. Это не означает завершённую приёмку всех его сочетаний.
- **Заявлено поставщиком**: возможность описана в официальном API, документации или публичном каталоге.
- **Нужно проверить**: отсутствует точная спецификация либо реальные ответы не проверялись.
- **Предлагается**: техническое решение этого исследования; оно не меняет согласованные решения проекта.

Документы поставщиков могут расходиться. Например, текущий публичный API Cerebras перечисляет Qwen 3.8 27B и GPT-OSS 120B, тогда как старая обзорная страница содержит другие модели. В выборе приоритет отдан актуальному API. Наличие модели в каталоге не подтверждает доступность на конкретном аккаунте.

В предыдущем ответе преобразование JSON Schema и эмуляция forced tool choice описывались преимущественно как предстоящая работа. Во время повторной проверки в рабочей копии уже появились `providerSchema`, `structuredTransport` и `forced_tool_choice`. Ниже они учтены как имеющийся код без отдельной приёмки в рамках этого исследования.

## 5. Общие изменения A–E

### A. Транспорт и адаптеры

Предлагаются общие обработчики Responses и Chat Completions с самостоятельными provider wrappers. Общий слой сериализует сообщения и разбирает протокол; wrapper определяет endpoint, auth, параметры, особенности ошибок, лимитов и usage. Не следует создавать один безусловный «OpenAI-compatible» adapter, обещающий одинаковую семантику всем поставщикам.

Для Cerebras/Groq базовый вариант — Chat Completions. Для Kie Kimi/DeepSeek — `/openai/v1/responses`. Kie Gemini использует собственный путь совместимого Chat Completions. Для Google Cloud нужен native Gemini transport. Смену транспорта не использовать как автоматический повтор после неизвестного исхода.

Параметры нельзя передавать общим бесконтрольным spread. Для каждого маршрута нужны допустимые поля, enum, обязательные значения и политика выходного лимита. Неподдерживаемый параметр должен давать ошибку до отправки, а не молча игнорироваться.

### B. Возможности модели

Вместо одних tools/schema flags требуется описание:

- native/эмулируемый forced tool choice; auto, none, required, named;
- один или несколько вызовов, parallel calls, допустимость текста рядом с вызовами;
- режим JSON object или JSON Schema, strict, поддерживаемые keywords и сочетания с tools/streaming;
- формат и пределы изображения, допустимые роли сообщений, обработка detail;
- reasoning controls, бюджет/effort, наличие continuation metadata;
- контекст, максимальный выход и реальная исполнимость ограничения выхода;
- кэш, доступные счётчики usage, возможность сверки стоимости;
- статус preview, alias/snapshot и дата проверки.

Проверки выполняются для каждого разрешённого варианта маршрута. Резервный text-only маршрут не должен принимать запрос с изображением. Эмуляция tool choice допустима по уже согласованному LF-D07, с отметкой способа исполнения. Она не означает поддержки произвольных схем и не отменяет refused.

### C. Оценка и расчёт

Оценивать нужно фактически отправляемое представление: инструкции, сообщения, tools, преобразованную JSON Schema, изображения и ожидаемый выход. `JSON.stringify(input)` плюс универсальный overhead не является точным tokenizer конкретного поставщика. Особое внимание — расхождению исходной и скомпилированной схемы при резервировании.

Для Qwen/Kimi/Gemini понадобятся точные счётчики, если доступны и соответствуют API, либо измеренные оценщики с указанием погрешности. `utf8_upper_bound` можно использовать как осторожную текстовую оценку, но он не доказывает границу расхода изображений и скрытого framing. Возвращать источник, версию, предположения и уверенность прогноза.

Модельные цены нужно публиковать неизменяемыми версиями. Включить вход без кэша, cache read/write при наличии, выход, reasoning и отдельные платные действия. Не суммировать reasoning второй раз, если provider completion/output tokens уже включают его. Не превращать отсутствующий счётчик в ноль.

У Qwen на Groq документировано 2048 входных токенов на изображение и до трёх изображений. Для Cerebras это правило не доказано. У Kie image accounting нуждается в отдельном подтверждении. У Gemini нельзя переносить OpenAI image-token formulas даже при использовании совместимого формата запроса. [Groq Qwen](https://console.groq.com/docs/model/qwen/qwen3.8-27b).

В текущем `inputTokens` есть ограничение сериализованного входа 2 MB. Перед обещанием контекста 1M проверить всю цепочку: HTTP body, assets, схемы сообщений, хранение, quoting, очередь, таймауты и SDK. Предельное окно поставщика не становится автоматически пределом UAI.

`estimated_actual` следует разрешать по опубликованным возможностям и политике, а не по имени провайдера. Прогнозный резерв, максимум пользовательского согласия, исполнимый provider limit и риск установки — разные величины. Для DeepSeek Kie, где `max_output_tokens` не действует, режим с обязательным ограничением этим параметром недопустим. Нужна явно подходящая финансовая политика; нельзя просто снять проверку и заявить capped billing.

### D. Полноценный диалог с tools

Существующий режим «ровно один вызов функции» полезен для типизированного результата и сохраняется. Полноценная история требует блоков вызова и результата инструмента, стабильных call IDs, поддержки ошибок инструмента и нескольких вызовов там, где это разрешено.

Исполнение инструментов остаётся в приложении по текущему решению. UAI передаёт историю и считает каждый вызов модели. Автономный agent loop не входит. Общий резерв динамической цепочки позже реализован как [резервный пул](QUOTING.md#резерв-на-составную-работу): каждый вызов модели по-прежнему отдельный request.

Для Gemini сохранять возвращаемые провайдером служебные данные продолжения, например thought signatures, если выбранный протокол требует их. Не восстанавливать подписи по тексту и не передавать служебные данные одному поставщику от другого. Проверить сохранение этих данных выбранным транспортом каждого Gemini-маршрута. Если нет, ограничить поддержку этим фактом или использовать другой документированный транспорт.

### E. Выполнение, лимиты и приёмка

Для каждого адаптера определить auth/quota/invalid/transient/refused/defect/unknown. Timeout после отправки не является доказательством отсутствия расходов. HTTP 200 тоже не гарантирует успех: проверить тело ошибки и терминальное событие. Не повторять неизвестный платный исход автоматически.

SSE должен разбирать фрагменты аргументов, текст и служебные события раздельно. Обрыв после выдачи текста, отсутствие final usage и обрыв после tool call — отдельные случаи. Выполнять инструмент по неполному JSON из потока нельзя. Generation ID нужно сохранять максимально рано, до финального ответа.

Задать лимиты запросов, токенов и параллельности на доступном уровне account/connection/model. Для неизвестных лимитов использовать явно выбранный консервативный режим, а не копировать OpenAI Tier 4. Наблюдения Retry-After и заголовков ограничений должны обновлять admission без повторного финансового списания.

## 6. Особенности Kie.ai

Kimi и DeepSeek имеют Responses-подобный интерфейс; общий транспорт переиспользуем, но параметры и счета различаются. Kimi документирует auto и named function choice. Общий required не заявлен. Для одного инструмента можно использовать named; для выбора одного из нескольких — согласованную эмуляцию через schema после проверки её поддержки. Встроенный web_search у Kimi не поддержан и, согласно документации, игнорируется; UAI должен отклонять такой запрос, если обещает эту возможность. [Kimi API](https://docs.kie.ai/market/kimi/kimi-k3).

У DeepSeek не поддерживаются `max_output_tokens`, `temperature`, `top_p`. Reasoning включён по умолчанию, поэтому прогноз ответа без него может недооценить расход. [DeepSeek API](https://docs.kie.ai/market/deepseek-v4-1-flash).

В Kie Gemini схема описывает Chat Completions, а пример ответа показывает Gemini `candidates`, `usageMetadata`, `thoughtSignature`. Это документальное противоречие. До живой проверки нужен статус «candidate», а parser следует строить по подтверждённому контракту. Нельзя считать все формы взаимозаменяемыми или заявить полную schema-поддержку по маркетинговой странице. [Gemini API](https://docs.kie.ai/market/gemini/gemini-3-8-flash-openai).

`credits_consumed` хранить отдельно от токенов, USD и пользовательских кредитов UAI. Нужны подтверждённая цена Kie, правило конвертации provider credits и понимание округления. Снижение общего баланса не является точной стоимостью одного запроса при параллельной работе. Для Gemini ставки карточек подтверждены в разделе 11; для Kimi/DeepSeek они остаются открытым вопросом. Финансовая приёмка каждого маршрута требует проверки usage, тарифа и фактического списания, даже если технический вызов проходит.

## 11. Варианты доступа к Gemini: скорость, квоты и стоимость

Дополнение от 25.09.2026. Под Key.ai понимается Kie.ai из исходного запроса. Проверены официальные документы Google/OpenRouter и интерфейс каталога Kie; платные запросы не выполнялись. Скорость и процент ошибок на нагрузке приложения не измерены. Наличие кабинета в браузере не использовалось как доказательство квот конкретного аккаунта.

### 11.1. Что означает «быстрый доступ»

Нужно различать задержку до первого токена, скорость генерации, суммарный пропускной объём и доступность мощности. Tier в AI Studio регулирует квоты; из низкого tier не следует искусственно медленная генерация каждого ответа. Длинный thinking и очередь могут увеличить ожидание даже при достаточном RPM.

У прямого Gemini API Tier 1 обычно включается сразу после привязки billing. Сейчас Tier 2 требует оплаченных $100 и 3 дней после первого успешного платежа; Tier 3 — $1000 и 30 дней. Учитываются расходы связанного Google Cloud billing account. Конкретные RPM/TPM/RPD нужно смотреть в AI Studio: они зависят от модели и аккаунта. Квоты привязаны к проекту, дополнительные ключи их не умножают. Возможен запрос увеличения без гарантии одобрения. [Google: rate limits](https://ai.google.dev/gemini-api/docs/rate-limits).

Это означает, что сначала стоит проверить фактический paid tier уже имеющегося billing account. Предположение «у нового ключа обязательно минимальная квота» может быть неверно. Публичные таблицы не заменяют доступные аккаунту значения.

### 11.2. Сравнение способов подключения

| Подключение | Как начать / получить скорость | Лимиты и ограничения | Дополнительный посредник и учёт | Что добавить в UAI |
|---|---|---|---|---|
| Gemini Developer API Standard | API key, billing; минимальное число настроек | Квоты проекта/модели, общий пул, возможны 429 | Нет; только Google billing и наш учёт | Native Gemini adapter, usage, изображения, tools/schema, pricing |
| Gemini Developer API Priority | Interactions API с `service_tier: priority`; preview | Собственная квота по умолчанию 0.3 от Standard, учитывается и общий трафик; не способ снять ограничения Tier 1 | Нет; повышенная ставка Google | Отдельный Interactions transport, фактически обслуженный tier, правила downgrade |
| Google Cloud Vertex / Gemini Enterprise Agent Platform Standard PayGo | Cloud project, IAM и global endpoint | Общий пул; baseline зависит от usage tier; превышение и всплески best effort | Нет; Google Cloud billing, сложнее первоначальная настройка | Cloud auth и refresh, project/location, native adapter, глобальные квоты |
| Google Cloud Priority PayGo | Приоритетный класс запросов без закупки фиксированной мощности | Shared capacity, доступность модели/локации; не гарантированная выделенная ёмкость | Нет; собственный тариф Google | Priority headers, tier pricing, учёт реально обслуженного класса |
| Google Cloud Provisioned Throughput | Заказать мощность для выбранной модели | Предсказуемая выделенная пропускная способность; обязательства и доступность зависят от заказа | Нет шлюза; появляется фиксированная стоимость мощности | Учёт capacity/overage, отдельная аллокация фиксированной себестоимости |
| OpenRouter | Пополнить баланс, выбрать Gemini; поставщики AI Studio/Vertex | Нет общего platform request cap для paid models, но остаются upstream 429, защита и in-flight spending budget | Есть собственный баланс и маршрутизация | OpenRouter wrapper, расходы/маршрут, usage, ошибки; отдельная интеграция посредника |
| Kie.ai | Ключ и credits, отдельные Gemini endpoints | Публичные chat-specific RPM/TPM/concurrency не подтверждены | Есть собственные credits; полностью убрать учёт посредника не получится | Kie wrapper, credits/usage, tools/continuation, сверка и нагрузочная приёмка |

Для Developer API Priority документация показывает Interactions API, а не простое добавление параметра к существующему GenerateContent. При нехватке Priority capacity возможен переход на Standard с соответствующей ценой; фактический класс определяется заголовком `x-gemini-service-tier`. Поэтому Priority решает вопрос задержки, но не гарантирует увеличенный объём. [Priority inference](https://ai.google.dev/gemini-api/docs/priority-inference).

У Google Cloud Standard PayGo опубликован Tier 1 при eligible spend организации $10–250 за последние 30 дней: baseline Pro 500k TPM, Flash/Flash-Lite 2M TPM. Это не гарантированный лимит для совершенно нового аккаунта без расходов. Кроме того, список поддерживаемых моделей этой страницы не перечисляет 3.8 Flash и исключает preview: переносить эти числа на новейшие модели без проверки нельзя. Global endpoint рекомендуется для доступа к общему пулу. [Standard PayGo](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/standard-paygo).

В отличие от этой страницы, список Priority PayGo уже включает 3.8 Flash и 3.1 Pro Preview. Поддерживаются global и US/EU multiregion, не отдельные regional endpoints; предусмотрен заголовок `X-Vertex-AI-LLM-Shared-Request-Type: priority`. Для решения «какой объём доступен сразу» нужно подтверждение по конкретной модели и Cloud account. [Priority PayGo](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/priority-paygo). Выделенная мощность приобретается отдельно через [Provisioned Throughput](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/purchase-provisioned-throughput).

OpenRouter может быть проще нового Cloud-проекта, но не выполняет пожелание убрать посредника: остаются баланс, upstream routing и финансовая сверка. «Нет лимита платформы» не означает «нет 429». При передаче своего Google key через любой BYOK-прокси исходные Google-квоты сами по себе не исчезают. [OpenRouter limits](https://openrouter.ai/docs/api/reference/limits).

Это соответствует 0% неуспешных событий только внутри показанного десятиминутного интервала по неизвестной методике Kie. Это не агрегат за сутки, не независимая оценка, не SLA и не доказательство нулевых ошибок на наших запросах. Число наблюдений не показано. Для Pro подтверждённая агрегированная статистика отказов не найдена; рейтинг карточки не является таким показателем.

Нельзя свести в один процент без разбивки: HTTP 429, 5xx, timeout/оборванный stream, неизвестный исход после отправки, safety refusal, неверную schema/tool call и неудовлетворительное качество. HTTP 200 с отказом модели тоже не означает успешную задачу приложения.

В общей документации Kie есть 20 новых generation requests за 10 секунд и 100+ одновременно выполняющихся задач. Контекст описывает создание асинхронных задач, поэтому переносить эти значения на синхронный Gemini chat нельзя. Модельные RPM, TPM, concurrent streams, очередь, deadline и правила оплаты неуспешных chat-запросов остаются неизвестными. [Kie getting started](https://docs.kie.ai/1973359m0).

Перед основным использованием нужны подтверждение этих лимитов и ограниченный оплачиваемый прогон. Предлагаемый протокол: одинаковый набор задач, отдельные группы text/vision/tools/schema, ступени параллельности и несколько временных окон; считать долю ошибок первой попытки и итоговый успех после разрешённых повторов, p50/p95 TTFT и полного времени, стоимость успешного результата. Нулевые ошибки на 100 запросах не доказывают надёжность 99.9%; для приблизительной верхней границы 0.1% при нуле наблюдаемых ошибок нужны около 3000 независимых наблюдений, а коррелирующие сбои всё равно требуют проверки во времени. Здесь такой прогон не выполнялся.

### 11.5. Доработки UAI и рекомендуемый выбор

Пожеланию обойтись без дополнительного учёта посредника лучше всего соответствует **прямой Google**. Собственный provider billing остаётся в любом платном варианте; новые credits, upstream routing и сверка посредника при прямом подключении не нужны.

1. По выбору владельца начать с Google Cloud Standard PayGo. Проверить доступность моделей и квоты Cloud account. Developer API через AI Studio остаётся альтернативой, а не выбранным первым подключением.
2. Предусмотреть Cloud Priority PayGo отдельным профилем поверх того же Cloud-подключения. Его включение и приёмка относятся к следующему этапу. Проверять capacity по точной модели; не подменять эту проверку словом Priority.
3. Если нужна гарантированная ёмкость, оценить Provisioned Throughput под реальную нагрузку. Это отдельное финансовое решение, не обычная смена API key.
4. Kie оставить кандидатом для экономичного маршрута после проверки ограничений и результатов. Подтверждённая низкая цена ещё не доказывает хорошую доступность.

Дополнительные работы поверх общей основы раздела 5: native Gemini `contents/parts`, сериализация function calls/results, сохранение `thoughtSignature`, изображения inline/file, schema и thinking settings; подсчёт prompt/candidates/thoughts/cache tokens без двойного учёта; safety/finish reasons и оборванные streams. Для Cloud — project/location, IAM/OAuth и обновление credentials. Для Priority — поддержанный transport, запрошенный/фактический service tier, downgrade, разные тарифы и квоты. Встроенный Google Search должен иметь отдельный финансовый профиль до включения.

Оценка дополнительного инженерного объёма: прямой Standard с полноценной локальной приёмкой 3–5 дней после общей основы; Cloud auth/routing ещё 1–2 дня; Interactions/Priority ещё 2–4 дня с проверкой возможностей выбранного API. Общая история tools из раздела 9 не включается повторно. Ожидание квот/закупки мощности и платная проверка оцениваются отдельно. Google Cloud Standard уже включён в общую оценку раздела 9; повторно прибавлять этот пакет не нужно. Оценка Interactions относится только к альтернативному Developer API, не к Cloud Priority.

Дополнительные критерии: AMS-A19 — сохранение Gemini continuation metadata; AMS-A20 — фактический tier и корректный тариф при downgrade; AMS-A21 — раздельные safety/HTTP/transport/schema ошибки; AMS-A22 — опубликованные лимиты подтверждены для модели/аккаунта, а capacity проверена на согласованной нагрузке. Эти критерии предложены, не пройдены.

## 12. Cloud: SLA и пример нагрузки

Уточнение 25.09.2026. Для Gemini действует [отдельный SLA](https://cloud.google.com/vertex-ai/generative-ai/sla): базовая месячная доступность 99.5%; для designated shorter-availability models — 95%. Preview и квотные ошибки исключены, если документация не говорит иное. Это договорный показатель доступности, а не измеренный процент успешных запросов. Provisioned Throughput имеет дополнительный latency SLO только для покрываемых моделей/endpoints и условий. Priority сам по себе не означает отдельный повышенный SLA.

Для планирования пользователей предлагается считать `RPM = TPM × 0.7 / T`, где T — среднее потребление учитываемых квотой токенов на запрос, а 0.7 — выбранный инженерный запас, не гарантия Google. Нужно подтвердить точный счётчик TPM и включить его стоимость для входа, изображений, выхода и reasoning согласно правилам модели. Ниже T задан как условная величина уже в единицах этого счётчика.

| Условный запрос T | Flash при 2M TPM: запросов/мин | Pro при 500k TPM: запросов/мин |
|---|---:|---:|
| 2 000 | 700 | 175 |
| 10 000 | 140 | 35 |
| 30 000 | 46 | 11 |

При одном запросе в минуту на пользователя числа совпадают с количеством одновременно активных пользователей с равномерной нагрузкой. При одном запросе в две минуты пользователей вдвое больше. При среднем времени ответа 15 секунд число одновременно выполняющихся запросов равно RPM/4: например, 140 RPM означает около 35 параллельных генераций. Одновременный резкий старт всех запросов этой моделью не покрывается. Три модельных вызова на одно действие пользователя примерно втрое уменьшают доступное число действий при равном T каждого вызова.

Эти расчёты используют baseline Standard из раздела 11 и не устанавливают квоту Priority или Gemini 3.8 Flash. Фактический throughput нового аккаунта и новейшей модели остаётся проверить. [Standard PayGo](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/standard-paygo).

[Cloud Priority](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/priority-paygo) доступен без предварительной закупки Provisioned Throughput. Для режима только Priority требуются headers `X-Vertex-AI-LLM-Request-Type: shared` и `X-Vertex-AI-LLM-Shared-Request-Type: priority`. Правило 0.3 от Standard относится к Developer API и не установлено для Cloud этим источником. Публичная страница Cloud Priority не задаёт отдельную численную таблицу квот.

[Cloud pricing](https://cloud.google.com/gemini-enterprise-agent-platform/generative-ai/pricing): global Priority Flash 3.8 до конца 2026 года — $1.35/$6.75 за миллион входных/выходных токенов; Pro 3.1 Preview до 200k — $3.60/$21.60, свыше — $7.20/$32.40. Выход включает reasoning. Это +80% к соответствующему Standard. Для non-global Flash ставка выше на 10%. Минимальный spend или обязательное ожидание для включения Cloud Priority на его странице не указаны; это не обещание автоматической доступности на любом новом аккаунте.


## 13. Выбранный первый этап: Cloud Standard с подготовкой к Priority

Зафиксировано по указанию владельца 25.09.2026. Объём сейчас — требования к будущей реализации.

| Область | Создать для Standard PayGo | Предусмотреть для будущего Priority PayGo |
|---|---|---|
| Подключение | Google Cloud provider/adapter, project, location с исходным global endpoint, IAM/OAuth и обновление credentials | Переиспользовать Cloud auth и native transport; отдельный провайдер для Priority не нужен |
| Профили моделей | Выбранные Gemini Pro/Flash после подтверждения точных IDs и доступности | Режим обслуживания как явная настройка профиля маршрута; отдельно проверять поддержку Priority моделью/location |
| Возможности | Text, vision, streaming, tools/schema, thinking и continuation metadata согласно подтверждённым capabilities | Сохранять те же внешние API/SDK-контракты там, где возможности совпадают |
| Тарифы и оценка | Cloud rate cards, контекстные пороги, reasoning/cache/image usage, резерв и settlement | Раздельные версии тарифов Standard/Priority; режим входит в quote и attempt evidence, дорогой режим не включается скрыто |
| Очередь и квоты | Лимиты подтверждённого аккаунта/модели, сглаживание всплесков, deadlines и классификация 429 | Лимиты по режиму; не переносить коэффициент 0.3 из Developer API в Cloud |
| Маршрутизация | Только выбранный Standard-профиль | Переключение на Priority через новый опубликованный профиль с его тарифом; автоматический платный fallback не включать по умолчанию |
| Наблюдаемость | Запрошенная модель, endpoint, service mode, usage, стоимость и исход попытки | Фактический класс обслуживания сохранять при наличии подтверждённых данных; отсутствие metadata не подменять предположением |
| Проверки | Локальные сценарии text/vision/tools/schema/stream, ошибки и финансовые инварианты; затем отдельный согласованный живой прогон | Контрактные проверки параметров режима и выбора тарифа сейчас; реальная приёмка Priority при его подключении |

Первый этап не требует Interactions API из Gemini Developer API, закупки Provisioned Throughput или включения Priority. Общую основу раздела 5 и историю tools переиспользовать. Точные квоты и SLA выбранной модели подтверждаются отдельно; публичная таблица Standard не заменяет проверку аккаунта.

Критерий готовности архитектуры: Priority добавляется Cloud-профилем, тарифами, параметрами запроса и собственной приёмкой, без второго независимого Gemini-адаптера и переделки финансового учёта. Реализацию специфичных для Priority механизмов можно отложить до следующего этапа.
