# План расширения универсальных вызовов UAI

Дата: 2026-09-25. Статус: реализация начата; критерии и этапы перечислены ниже. Исходная проверка выполнена на UAI `6745373`. Последующие изменения сверять перед началом каждого этапа.

## 1. Цель и границы

Дать приложениям единый вызов с мультимодальным контекстом, инструментами, проверяемым структурированным результатом, стримингом и настраиваемыми условиями исполнения. Использовать существующие очереди, учёт, идентификацию и хранилище UAI.

UAI не получает сущностей директора, персонажа, раунда или обсуждения. Приложение выбирает контекст, роли, модели из разрешённых маршрутов, права и действия после результата. Настройки продуктовых действий хранятся в приложении и передаются серверным SDK. Инструменты исполняет приложение. Изображения и мокапы, требующие подтверждения человеком, продолжают проходить через quote и принятие операции; новые текстовые возможности не должны обходить эту границу.

До первого совместного запуска UAI и LogoPanel обратная совместимость не требуется. Контракты, SDK, конфигурации и тесты обновляются согласованно, без legacy-веток или дополнительных версий только ради прежнего поведения. Финансовая идемпотентность, фиксация условий исполняемого запроса и защита от повторной отправки неизвестного исхода остаются обязательными.

Этот план не разрешает реализацию продуктовой логики в репозитории LogoPanel, изменение действующих подключений, платные вызовы или развёртывание. Их проверки перечислены как отдельные этапы готовности.

## 2. Согласованные решения

| ID | Решение |
|---|---|
| UI-D01 | Дефолты обязательны. Порядок: дефолт UAI, выбранный профиль, параметры конкретного вызова. Отсутствие параметров и `{}` эквивалентны. Частичное переопределение наследует остальные поля; некорректные значения отклоняются. |
| UI-D02 | Дефолтный общий срок — 300 секунд от принятия, включая очередь, выполнение и повторы. Максимум — 4 попытки вместе с первой. Согласованный абсолютный предел установки равен 8; запрос и профиль не могут его повысить. |
| UI-D03 | Короткие повторы учитывают Retry-After и общий срок. Длинное восстановление по умолчанию выключено. Смена модели, повтор проверки схемы и перезапуск worker не обнуляют общий счётчик. |
| UI-D04 | OpenAI и Anthropic входят в первую поставку текстового сценария. Межпровайдерное переключение допустимо только по явно заданному маршруту с совместимыми возможностями. |
| UI-D05 | Для автоматических текстовых вызовов LogoPanel используется estimated_actual: прогнозный резерв, фактическое списание, возможный долг. При долге новые вызовы получают insufficient_credits. |
| UI-D06 | Инструменты описываются входом, результат содержит разобранный вызов. Режим «ровно один» проверяется UAI. Автоматического исполнения инструментов и tool loop в UAI нет. |
| UI-D07 | JSON Schema проверяется UAI. Технический дефект восстанавливается в пределах принятой политики за счёт платформы. Семантическая доработка валидного ответа не является техническим повтором. |
| UI-D08 | Отказ модели — отдельный конечный исход refused. Оплата определяется принятой политикой; отказ не вызывает автоматического повтора или обхода через резервную модель. |
| UI-D09 | При разрешённом повторе после показа текста новая попытка сбрасывает предварительный текст. Итоговый валидный результат является источником истины. |
| UI-D10 | Кэш имеет раздельные read/write counters, а прогноз резерва может учитывать ожидаемое попадание. Попадание не гарантируется; промах допустим в рамках estimated_actual. |
| UI-D11 | Оригиналы изображений и ресайз для LogoPanel принадлежат LogoPanel. В UAI исходные байты передаются без преобразования по умолчанию; ресайз, поворот и перекодирование включаются явно. |
| UI-D12 | Input assets используются повторно в разных запросах одного владельца. Для обсуждённого сценария срок хранения — 7 дней без использования с продлением. Это настройка, а не константа общего механизма. |
| UI-D13 | wallet.updated следует за финансовыми изменениями; available уже исключает резервы и учитывает долг. Предупреждение об остатке рассчитывает приложение. |
| UI-D14 | Эмбеддинги входят в общий план отдельной capability; их реализация не блокирует готовность текстового сценария. Постоянные векторы и поиск принадлежат приложению. |

Предыдущие значения `2+2`, три recovery-цикла и 16 attempts в существующей документации описывают прежнюю реализацию. При реализации UI-D02/UI-D03 заменить их согласованно в спецификациях, runtime и конфигурации, а не сохранить вторую систему исполнения.

## 4. Рекомендуемый контракт

Названия новых полей ниже являются предложением реализации, а не существующим API.

### Вызов

- `input`: упорядоченные сообщения с текстовыми и image-блоками, instructions, определения инструментов, tool_choice, response_schema. Asset может стоять в конкретном месте сообщения.
- `execution`: deadline, max_attempts, backoff, причины безопасного повтора, разрешение новой попытки после предварительного вывода. Маршрут выбирается из доступных приложению; произвольные подключения клиента не принимаются.
- `billing`: режим расчёта и правило оплаты refused. Опции разрешаются конфигурацией установки и профиля, не произвольным недоверенным клиентом.
- `delivery`: запрос потока и выбранные строковые поля структурированного результата. Для поля используется общий путь, например `/message`; сущность message не зашивается в UAI.
- `parameters`: поддерживаемые параметры модели, отдельно от правил исполнения. `expected_output_tokens` прогнозирует расход; явный предел генерации является другим параметром.

Дефолты относятся к необязательным настройкам. Они не отменяют обязательный вход и выбор доступной модели/профиля. Не наследовать массивы по индексам: явные списки заменяются целиком, объекты политики объединяются по известным полям схемы. `null`, неизвестное поле, отрицательный срок и max_attempts=0 — ошибки, а не отсутствие значения.

Проверка до резерва должна охватить все допустимые варианты маршрута: tools, выбор инструмента, схема, картинки, кэш, параметры и метод расчёта. Не удалять неподдерживаемое ограничение для успешного failover. Не расширять неявно текущую поддержку JSON Schema: сначала общий явно описанный набор обоих адаптеров с отказом на неподдерживаемое сочетание.

### Политика и её хранение

| Слой | Место и ответственность |
|---|---|
| Дефолты и именованные политики | JSON в Git UAI, публикация через общий механизм configuration; пример нового файла `configurations/execution/default.json` |
| Активные определения | БД UAI после validate/preview/publish/activate; история изменений нужна для аудита и воспроизводимости |
| Пределы установки | Оперативная конфигурация БД: max_attempts=8, лимиты сроков/потерь/размеров/подписок. План не предполагает повышения согласованного предела попыток. |
| Продуктовые настройки | Репозиторий и сервер LogoPanel; в UAI отсутствуют имена и логика ролей |
| Принятые условия | Snapshot запроса: итоговая политика, варианты маршрута, расчётные условия каждого варианта, принятие и deadline_at |

Один параметр имеет один источник редактирования. Файловые политики показываются в админке без второго независимого редактора; оперативные пределы редактируются в БД. Выходящие за пределы настройки отклоняются до принятия, а не молча урезаются.

Для четырёх попыток предлагается экспоненциальный backoff с базой 1 секунда: 1, 2, 4 секунды и ограниченный jitter. Третья задержка — техническое продолжение ранее предложенных 1/2 секунд, не новый цикл восстановления. Настройки base/multiplier/cap задаются политикой. При Retry-After за границей deadline новую попытку не запускать.

Изменение конфигурации не переписывает snapshot активного запроса. Абсолютные оперативные ограничения повторно проверяются перед dispatch; уменьшение предела не разрешает дополнительный вызов. Это контроль текущего исполнения, а не поддержка старого API.

### Результат и расчёт

Возвращать типизированный вид результата: текст, разобранный структурированный объект, разобранный tool call или refused. Отдельно сохранять execution_status и settlement_status: наличие результата не доказывает, что неизвестный usage уже рассчитан.

Tool call содержит стабильный UAI ID, имя и разобранные аргументы. ID не меняется при повторном получении финального результата; исходный ID провайдера хранится отдельно при наличии. Приложение проверяет права, актуальное состояние и идемпотентность исполнения. UAI не вызывает функции приложения.

Usage возвращается для конкретной попытки и как явно обозначенная сводка запроса: uncached/read/write/output, model/provider, известность показателей. Себестоимость неудачных попыток и клиентское списание не смешиваются. Денежные суммы передаются целочисленными строками.

Для refused поддержать `platform` и `actual_usage` в billing-политике. Владелец утвердил дефолт `platform` 2026-09-25; приложение может явно выбрать `actual_usage`. Неизвестная себестоимость отказа не становится нулевой.

## 5. Этапы реализации

### UI-I00. Контракты, дефолты и согласованная спецификация

1. Вынести схемы политик, мультимодального входа, tools, результатов и событий в contracts. Задать разрешённое сочетание tools/response_schema по возможностям модели; не обещать произвольное сочетание.
2. Реализовать одну чистую функцию разрешения дефолтов и ограничений. Использовать её в quote, invocation и создании request внутри принятой операции.
3. Расширить конфигурационные определения, публикацию, активные bindings и discovery capabilities. Добавить поля для идентичности принятой политики и per-variant snapshots.
4. Обновить OpenAPI и сгенерированные SDK-типы. Поддержка старых форматов не нужна.
5. Согласованно обновить DECISIONS, API, EXECUTION, QUOTING, MODEL_PRICING_SPEC, FILE_CONFIGURATION, README и IMPLEMENTATION. Сохранить прежние requirement/acceptance ID; новые проверки получают UI-Axx.

Файлы: `packages/contracts/api.ts`, `packages/providers/src/contracts.ts`, `packages/catalog/src/index.ts`, `packages/configuration/src/index.ts`, `packages/quoting/src/index.ts`, `apps/api/src/profiles.ts`, `scripts/generate-openapi.ts`, `scripts/generate-configuration-schema.ts`, новые миграции в `migrations/`. Обновить проверяемые generated artifacts `docs/openapi.json`, `configurations/schema.json` и `packages/sdk/src/generated/`.

Готовность: отсутствие блока, `{}` и эквивалентное частичное наследование дают одинаковые effective conditions; ошибочные параметры отвергаются до резерва. Публикация не требует сущностей LogoPanel. Проверить путь publish → active profile serializer → SDK: policy/capability-поля не должны исчезать из discovery.

### UI-I01. Конечные попытки, маршруты и отказ модели

1. Заменить жёстко заданные retry/recovery slots, количество циклов и задержки повторной генерации общей политикой выбора следующей попытки. Не заменять механически совпадающие числа в сроках наблюдения или финансовой сверки. Поддержать конечную явно заданную recovery-конфигурацию, но дефолт оставить выключенным. Recovery использует тот же общий счётчик.
2. Резервировать номер отправки атомарно до обращения к провайдеру под существующими блокировками/fencing. Если процесс упал после допуска к отправке, не обнулять номер и не угадывать, что внешнего вызова не было.
3. Повторная доставка job и повтор HTTP с тем же idempotency key не создают новую оплаченную попытку. Ожидание квоты до отправки, lookup и polling исходного job не являются повторной генерацией; у наблюдения остаются собственные конечные сроки.
   Отключить скрытые повторы платного submit в HTTP/provider SDK: каждая новая отправка должна пройти единый допуск и счётчик UAI.
4. Для подтверждённого дефекта после output_started разрешать следующую попытку только при принятой политике и поддержке reset. Для unknown, canceled, refused и окончательных ошибок не запускать повторную генерацию.
5. Нормализовать refused отдельно, добавить terminal status во все проверки API, SDK, queue, admin, demo и расчёта. Применять принятую billing-политику идемпотентно.
6. Сохранять совместимые параметры, ставки и markup каждого варианта маршрута. Расчёт удачной попытки использует принятые условия её модели. Неудачные технические попытки учитываются как расходы платформы и ограничиваются её risk budget.

Предел 8 относится к числу попыток одного request и не совпадает с лимитом одновременных workers/слотов. Выключение длинного retry recovery не отключает наблюдение исходного native job, reconciliation или финансовое закрытие unknown. Проверить отдельно существующие таймауты submit/observation, чтобы они не отменяли принятую политику неожиданным внутренним ограничением.

Файлы: `packages/execution/src/index.ts`, `packages/execution/src/runtime.ts`, `packages/execution/src/default-runtime.ts`, `packages/queue/src/`, `packages/catalog/src/index.ts`, `packages/quoting/src/index.ts`, `packages/providers/src/`, `packages/accounting/src/index.ts`.

Готовность: concurrent workers, рестарт, fallback и дефектный JSON не превышают 4 попытки по дефолту и предел установки; max_attempts=1 запрещает повторы; unknown остаётся исходной попыткой.

### UI-I02. Оригинальные изображения и повторно используемые assets

1. Разделить проверку изображения и преобразование. В preserve-режиме проверять digest, тип, размер, декодируемость и ограничения модели, но передавать те же bytes, включая исходную ориентацию/метаданные.
2. Оставить существующий resize как явный transform. Не выполнять rotate, padding или toFormat без согласованной настройки. Ограничение размера означает отказ, а не скрытый ресайз.
3. Считать input tokens по фактическим размерам и настройкам отправки. Удалить зависимость обязательной подготовки от расчёта цены; текущие предположения о квадрате 1024×1024 нельзя применять к произвольному оригиналу.
4. Расширить upload input-asset retention и generic project binding. Фиксировать last_used_at при принятом использовании; обычный GET и отклонённый запрос не продлевают срок. Предусмотреть явное продление авторизованным приложением. Начальный TTL новой доступной копии считается от завершения upload.
5. Добавить ссылки удержания из принятых запросов, защищающие assets от обычной TTL-очистки до окончания использования. ACK результата не удаляет общий input asset, нужный другим вызовам.
6. Удаление проекта закрывает новые обращения, отменяет неотправленные запросы и запрещает позднюю выдачу контента. Очистка удержанных файлов после освобождения ссылок не должна воскрешать удалённый проект.
7. Истёкшую копию приложение загружает снова из своего оригинала. Output asset по-прежнему передаётся приложению для хранения и последующей загрузки как input; прямое превращение output в долговечный input не входит в этот этап.

Файлы: `packages/quoting/src/prepare-model-assets.ts`, `packages/model-pricing/src/index.ts`, `packages/model-pricing/src/examples.ts`, `packages/storage/src/index.ts`, `apps/api/src/server.ts`, `packages/contracts/api.ts`, `packages/sdk/src/index.ts`, настройки preparation в админке и configuration.

Готовность: хэш исходных байтов совпадает с хэшем декодированного вложения запроса провайдеру; явный transform меняет только заявленные свойства; asset повторно используется и очищается без нарушения активного выполнения. В UAI не создаётся каталог вариантов изображений LogoPanel.

### UI-I03. Мультимодальный текст, инструменты и схемы на двух адаптерах

### UI-I04. Упорядоченный поток одного вызова

1. Ввести событие попытки и delta envelope с request_id, attempt_id, монотонным номером попытки, fencing/generation, sequence и field_path. Sequence увеличивается внутри попытки для всех её дельт независимо от поля. Управляющие события не содержат текст; payload дельт остаётся временным.
2. Сериализовать проверку доступа и отправку внутри одного потока. Отклонять дельты старого worker/attempt после смены fencing token. Начало попытки с большим порядком сбрасывает предыдущий предварительный текст. Даже при потере attempt/reset SDK обнаруживает новую попытку по envelope, сбрасывает текст и отмечает пропуск; дубли и запоздалые дельты игнорируются.
3. Для нового вызова реализовать единый streaming invocation endpoint: общий LISTEN и подписчик готовы до commit принятия, accepted выдаётся первым, ранние дельты ограниченно буферизуются до accepted. Для переподключения сначала зарегистрировать подписчика известного request, затем прочитать snapshot попытки/результата, согласовать накопленный буфер по generation/sequence и только затем продолжить выдачу. Завершение или смена попытки в этом интервале не должны теряться; после выдачи terminal result дельты запрещены. Не полагаться на POST, за которым клиент успеет сделать GET events.
4. Использовать общий LISTEN на API-процесс и ограниченные буферы подписчиков, а не отдельное соединение БД на каждого подписчика. Медленный клиент отключается с возможностью прочитать итоговый результат, не блокируя провайдера.
5. Добавить инкрементальный parser для выбранных строковых полей JSON. Обработать разрывы UTF-8, escapes, unicode, ключей и строк между chunks. Поле message не должно быть особым случаем в parser.
6. SDK предоставляет ai.stream как async-итератор и onDelta/onAttempt в ai.run поверх общего механизма. Разрыв транспорта не отменяет генерацию и не создаёт новый invocation. Явная отмена остаётся отдельным действием.
7. Итоговый result целиком заменяет предварительный текст; persist вызывается до ACK. При потере дельт SDK помечает live-показ неполным и не выдаёт его за сохранённый результат. Для быстрой реплики приложение располагает message первым в схеме; раннюю генерацию поля проверяют на выбранных моделях.

Файлы: `apps/api/src/server.ts`, `packages/execution/src/default-runtime.ts`, `packages/execution/src/runtime.ts`, `packages/contracts/api.ts`, `packages/sdk/src/index.ts`, новый модуль transient event hub и parser.

Готовность: первая дельта не теряется из-за гонки запуска, порядок сохраняется при медленных проверках доступа, смена попытки не склеивает ответы, reconnect не расходует дополнительную попытку. Дельты не попадают в долговечный финансовый outbox.

### UI-I05. Префиксный кэш, usage и прогноз резерва

1. Добавить к блокам provider-independent hints стабильного префикса. Адаптер обязан обозначать поддержку explicit boundaries или автоматического cache: не обещать одинаковую механику двух провайдеров.
2. Построить безопасную идентичность префикса из owner scope, модели/подключения, порядка и содержимого блоков, tools/schema, параметров обработки изображений и digest bytes. Изменение схемы/инструментов/изображений инвалидирует соответствующее предположение.
3. Хранить только ограниченные metadata наблюдений: digest, время, scope, модель, подтверждённые counters и срок полезности. Не создавать второе постоянное хранилище prompts и не объявлять provider cache гарантированным.
4. Для холодного или неподтверждённого префикса использовать холодную оценку. Для обоснованного ожидаемого попадания разделять прогноз uncached/read/write и output. Сохранять expected estimate, cold estimate и confidence; резервировать прогноз в estimated_actual.
5. При fallback на другую модель/подключение сбрасывать неподтверждённое ожидание попадания. Условия маршрута должны учитывать возможный холодный расход; исходный резерв не становится жёстким потолком фактического списания.
6. Нормализовать публичный usage без домысливания отсутствующих counters. Не считать cache write нулём только из-за отсутствия поля. Отдельно проверять значение total input и разбиение по документации/наблюдениям конкретной модели.
   Тарифное разбиение сохраняет категории записи с разными ставками/TTL, если модель их предоставляет. Cached input не оплачивается второй раз как uncached; rounding выполняется по принятой методике, а ставки каждой категории входят в snapshot варианта маршрута. Суммарный cached counter не считается доказательством попадания всего отмеченного префикса.
7. Сохранять insufficient_credits как отказ до dispatch, отдельно от provider allowance/quota и backpressure. Добавить типизированный SDK-код/guard для уже существующего insufficient_credits. Параллельные принятые вызовы могут завершиться с совокупным долгом; предупреждение приложения не является финансовой блокировкой.

Файлы: `packages/providers/src/usage.ts`, `packages/quoting/src/estimation.ts`, `packages/quoting/src/index.ts`, `packages/model-pricing/src/`, `packages/execution/src/runtime.ts`, `packages/contracts/api.ts`, `packages/sdk/src/index.ts`, новые metadata-таблицы.

Готовность: тёплый прогноз допускает вызов при остатке ниже холодной оценки; промах приводит к правильному actual charge/долгу без двойного списания; смена провайдера не использует чужую cache-сессию. Не фиксировать обещания «в десять раз» или «в четыре раза дешевле» без измерений.
