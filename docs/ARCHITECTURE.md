# Архитектура

[Оглавление](README.md)

## Граница продукта

Приложение знает, зачем нужен ответ. Платформа знает, как выполнить разрешённый запрос, ограничить его расход, получить результат и записать использование.

Приложение хранит предметные проекты, промпты, историю и последовательность действий. Платформа хранит только необходимые для выполнения входные данные, результаты с ограниченным сроком хранения, технические метаданные и финансовые записи. Копия всей базы приложения не нужна.

Платёжный сервис хранит покупки, розничные цены, подписки и денежные возвраты. Он выпускает команды начисления или отзыва кредитов. AI-платформа не проверяет карточные платежи и не изменяет тарифные планы.

~~~mermaid
flowchart LR
  APP[Приложения] --> API[API и SDK]
  PAY[Платёжный сервис] --> WAL[Кошелёк]
  API --> QUOTE[Оценка и разрешение операции]
  QUOTE --> WAL
  QUOTE --> QUEUE[Очередь и маршрутизация]
  QUEUE --> ADAPTERS[Адаптеры]
  ADAPTERS --> PROVIDERS[Поставщики]
  ADAPTERS --> USAGE[Использование и себестоимость]
  USAGE --> WAL
  SYNC[Сверка] --> PROVIDERS
  SYNC --> EVENTS[События и инциденты]
  ADMIN[Административный интерфейс] --> API
~~~

## Развёртывание

Центральный каталог хранит опубликованные версии моделей, схемы параметров, подготовку вложений, методики оценки и отдельный блок pricing каждой модели. `packages/model-pricing` исполняет ограниченные типы tokens/per_unit/lookup/formula и считает точными рациональными числами. Ставки поставщика версионируются отдельно. Администратор проверяет несохранённый расчёт без вызова поставщика; публикация проверяет покрытия, контрольные количества и заданные ожидаемые стоимости.

Quoting связывает окончательную цену `quoted_final` с конкретным входом и версиями, accounting обеспечивает резерв и однократное списание, execution сохраняет расход каждой попытки независимо от клиентской цены. Фактическая себестоимость не переписывает согласованную цену. Публичный каталог передаёт клиенту параметры и подготовку файлов, но не внутреннюю методику или коэффициенты. Подробнее: [центральный расчёт цены](MODEL_PRICING_SPEC.md).

Одна самостоятельная кодовая база на TypeScript, развёрнутая отдельно для каждого собственного приложения. У Logo Panel будет свой экземпляр. Установки имеют независимые PostgreSQL, временные BlobStore, конфигурации, service tokens и ключи поставщиков. Они не обращаются к базе друг друга и не делят пользовательские кошельки.

Внутри установки API, worker и scheduler имеют отдельные точки запуска, используют общие контракты и одну PostgreSQL. Административный интерфейс является отдельной сборкой. BlobStore имеет локальную реализацию для разработки и объектное хранилище для сервера. Публичная регистрация сторонних разработчиков и централизованный SaaS control plane не входят в v1.

~~~text
uai/
  apps/
    api/
    worker/
    scheduler/
    admin/
    demo/
  packages/
    contracts/
    ui/
    sdk/
    providers/
    catalog/
    pricing/
    quoting/
    execution/
    accounting/
    reconciliation/
    notifications/
    storage/
  migrations/
  docs/
~~~

В первой версии долговечная очередь живёт в PostgreSQL. Worker берёт задания через короткие транзакции и аренду выполнения. Сетевой запрос к провайдеру не удерживает блокировку строки кошелька. Если позднее появится Redis, PostgreSQL остаётся источником финансового состояния и задач, требующих восстановления.

Событие для внешней доставки записывается в outbox в той же транзакции, что и изменение состояния. Доставка может повторяться. Получатели устраняют дубли по event_id.

## Интерфейсы и тестовый клиент

apps/admin и apps/demo используют TanStack Start и shadcn/ui. packages/ui содержит общие компоненты, тему, типографику и форматирование сумм/статусов. Конкретные версии зависимостей фиксируются при создании каркаса; сборка и запуск проверяются в выбранном окружении.

Серверный слой TanStack Start обслуживает сессии и вызовы UAI от имени разрешённого пользователя. Админка работает через административный API, demo через SDK. Серверные функции интерфейсов не изменяют таблицы UAI напрямую и не заменяют самостоятельные API, worker и scheduler. Авторизация финансовых команд проверяется в API UAI независимо от видимости кнопок.

Demo владеет собственной историей чатов и постоянными файлами, использует отдельную базу или изолированное хранилище клиента и не читает базу UAI. После долговечного сохранения результата backend вызывает acknowledge. Удаление диалога удаляет клиентский контент и инициирует удаление временного контента UAI, сохраняя финансовую историю.

Тестовое начисление доступно только авторизованному тестовому пользователю для его аккаунта и только при включённом серверном режиме тестового окружения. Backend использует отдельный токен с правом grant и ограниченной областью. Он проверяет положительную сумму и настроенный верхний предел, задаёт явный expires_at и reason, повторяет команду с тем же Idempotency-Key. В production маршрут начисления demo отключён независимо от frontend. Начисление создаёт кредитный пакет и не пополняет счёт провайдера.

Требования к оформлению заданы в [OPERATIONS](OPERATIONS.md), сценарии клиента и приёмка в [IMPLEMENTATION](IMPLEMENTATION.md).

## Модули и владельцы данных

| Модуль | Владеет | Не принимает решения о |
|---|---|---|
| Connections | Аккаунты поставщиков, credential refs, возможности сверки, состояние | Розничной цене |
| Catalog | Версии моделей, capabilities, допустимые параметры | Промптах приложения |
| Pricing | Rate cards, правила расчёта себестоимости, история | Проданных подписках |
| Quoting | Рецепты, оценки, принятые ограничения | Последовательности предметного workflow |
| Execution | Requests, attempts, очередь, маршруты, лимиты | Выпуске кредитов |
| Accounting | Usage, cost entries, lots, reservations, postings | Подтверждении платежа |
| Reconciliation | Снимки поставщиков, периоды, расхождения | Автоматическом пересчёте пользовательских списаний |
| Notifications | Инциденты, правила, доставки | Повторе генераций |

Один модуль не изменяет таблицы другого напрямую. Для критических операций допускается общий application service, который вызывает модули в одной транзакции, например создание операции и резерва.

## Идентичность и изоляция

- organization_id обозначает владельца подключений и платформенного пространства.
- application_id обозначает клиентское приложение.
- account_id обозначает плательщика расхода внутри приложения, человека или команду.
- actor_id обозначает конкретного инициатора и используется для аудита и дополнительных лимитов.
- wallet_id обозначает кошелёк аккаунта в конкретной кредитной единице.
- external_project_id является необязательной меткой приложения. Она не даёт прав доступа и не управляет временем жизни финансовых записей.

Все чтения и изменения ограничиваются organization и разрешёнными application/account. Сервисный ключ приложения не даёт доступ к другим приложениям. Browser не получает ключ AI-платформы с правами начисления или выполнения произвольного запроса.

Аккаунты создаёт доверенный backend приложения. Если в будущем нужен прямой вызов из браузера, backend выпускает короткоживущий ограниченный токен для конкретного аккаунта, операции и бюджета. Это расширение не требуется для первой интеграции Logo Panel.

Реализованный [контракт внешней авторизации](EXTERNAL_AUTH.md) сохраняет server-to-server границу: backend родителя проверяет человека, membership и продуктовые права, затем SDK передаёт ограниченный контекст. UAI не хранит пользователей и состав команд. `audit_identity` сохраняет внешнего человека, команду и service principal отдельно от исторического `actor_id`. Личность инициатора и плательщик принятой операции не изменяются вместе с активной сессией.

Основная конфигурация содержит одно application на установку и несколько клиентских accounts. Organization/application scope сохраняется в контрактах для изоляции и последующего расширения. Общий wallet нескольких приложений внутри одной установки потребует отдельного разрешения и не нужен для первой интеграции. Между установками общих кошельков нет. Нельзя переносить кредиты между организациями или кредитными единицами обычной командой начисления.

## Подключение, модель и маршрут

Provider обозначает реализацию интеграции, например OpenAI. Connection обозначает конкретную организацию, проект или аккаунт у поставщика и ссылку на его credentials. ModelVersion обозначает реальную модель с возможностями. RouteVersion обозначает утверждённую стратегию выбора моделей и connections.

Лимиты могут принадлежать connection, организации поставщика или общей группе моделей. Несколько ключей одного аккаунта не означают несколько независимых бюджетов или rate limits.

Каждая установка получает отдельный ключ. Если аккаунт поставщика общий, оператор назначает установкам части общего бюджета и квоты так, чтобы сумма выделенных долей не превышала известный общий предел с запасом. Это локальное ограничение, а не распределённый точный счётчик. Внешний расход и изменение provider limits всё ещё могут вызвать 429; scheduler обрабатывает их по EXECUTION. Финансовые snapshots общего аккаунта помечаются своим scope и не выдаются за расходы одной установки.

Приложение обычно обращается к профилю, например text.medium или image.standard. Профиль разрешается в конкретную версию маршрута при оценке. В каждой попытке сохраняются фактические provider, connection, model, параметры и применённые версии цен.

Профиль не обещает одинаковое качество моделей. Разрешённые замены утверждаются администратором после оценки качества и совместимости. Жёсткая фиксация конкретной модели также поддерживается.

## Контракт адаптера

Каждый адаптер публикует возможности, а не имитирует отсутствующие функции.

| Метод | Назначение |
|---|---|
| capabilities | Виды запросов, streaming, native jobs, lookup, cancel, идемпотентность, usage и финансовые API |
| validate | Проверить сочетание модели, параметров, файлов и схемы |
| estimateUsage | Оценить оплачиваемые величины и консервативный предел |
| estimateLimitUsage | Отдельно оценить расход rate limits |
| execute | Выполнить одну попытку и вернуть результат или handle задачи |
| poll / cancel | Использовать нативную задачу поставщика, если поддерживается |
| normalizeUsage | Сохранить исходные данные и построить непересекающиеся billable items |
| classifyFailure | Различить временный лимит, квоту, auth, invalid request и неизвестный исход |
| readRateLimits | Прочитать доступные заголовки и конфигурацию лимитов |
| readUsage / readCosts / readBalance | Получить только поддерживаемые отчёты с областью и временем покрытия |

Lookup по request ID поддерживается только там, где его документирует API. Корреляционный request ID в заголовке сам по себе не означает возможность получить результат.

Платформа различает текст, image generation/edit, speech synthesis, search, embeddings и специализированную зарегистрированную операцию. В первой реализации активируются только используемые capabilities. Универсальность контракта не требует немедленно реализовать все модальности.

Произвольный provider endpoint, секрет, команда shell или исполняемый код не принимаются от конечного пользователя. Специализированные workers регистрирует администратор, они запускают заранее установленную реализацию и сообщают usage по подписанному доверенному каналу.

## Файлы и хранение содержимого

Приложение загружает файл и получает asset_id. Платформа проверяет владельца, формат, размер и готовность файла перед вызовом. Удалённый provider URL не считается готовой передачей: платформа проверяет и сохраняет результат во временном хранилище, прежде чем объявить ready. Постоянное хранение проектов, ответов и файлов принадлежит приложению.

Внешние URL разрешаются только согласно политике загрузок. Нужны защита от запросов к внутренней сети и проверка перенаправлений. Для контролируемых интеграций предпочтительны asset_id и подписанные загрузки.

Секреты хранятся через credential refs и шифрование на сервере. В журнал, SDK-ответ и webhook не попадают ключи или authorization headers. Admin credentials сверки доступны scheduler, но не обязательно worker генерации.

После долговечного сохранения ответа и всех его файлов приложение вызывает acknowledge с ID версии результата и hashes. Платформа закрывает доступ к этим временным копиям и ставит физическое удаление в надёжную очередь. Повтор acknowledgement безопасен. Скачивание, SSE disconnect и получение HTTP 200 сами по себе не являются подтверждением сохранения.

В v1 output asset предназначен только для передачи и не принимается как input asset следующего request. Приложение сохраняет файл и загружает отдельный input asset при следующем вызове; SDK может выполнить эту передачу. Так acknowledgement не удаляет файл из-под уже принятого потребителя. Общие ссылки активных requests допускаются только на явно загруженный input asset. Оптимизация серверного копирования с отдельными ссылками владения отложена.

Если acknowledgement не пришёл, результат удаляется по content_expires_at. Предлагаемый стартовый TTL: один час с ready_at, зафиксированный при принятии операции и возвращаемый в API. GET, повтор команды и переподключение не продлевают срок. Валидный результат, доступный в обещанное окно, оплачивается независимо от acknowledgement; клиент не может обнулить расход, отказавшись подтверждать загрузку. Ошибка выдачи на стороне платформы разрешается по часовому правилу ACCOUNTING.

Inputs и дефектные промежуточные результаты хранятся только пока нужны активной задаче и ограниченному восстановлению. Общие входные assets имеют ссылки на принятые requests и удаляются после завершения последних потребителей, без бесконечного продления новыми чтениями. Неиспользованная загрузка истекает по upload expiry. Финансовое разбирательство само по себе не продлевает хранение содержимого. Все пути имеют конечный deadline; истечение не запускает повторную генерацию.

Команда удаления содержимого проекта сначала устанавливает tombstone, запрещает новые requests в этой версии проекта и отменяет ещё не отправленные. Вызовы, уже ушедшие поставщику, проходят отдельный cancel/settlement; их поздние результаты не могут восстановить удалённый контент. Для использования того же внешнего имени создаётся новый project generation. Журнал usage и сумм сохраняется без prompts, ответов и файлов.

Очистка охватывает BlobStore, текстовые результаты в БД, временные файлы, response caches, outbox payloads и диагностические данные. Долговечные события содержат ссылки и metadata, а не копии ответов; финансовый raw usage очищается от контента при записи. Signed URLs не должны переживать срок доступа к контенту. Очередь purge проверяется и повторяется после сбоев. Временное содержимое не включается в долговременный финансовый backup; после restore сначала применяются tombstones и expiry, только затем открывается чтение. Сроки хранения минимального журнала и backup задаются отдельно до production.

## Подключение нового приложения

1. Создать application и ограниченный service principal.
2. Создать account/wallet либо сопоставить внешний аккаунт.
3. Выбрать разрешённые маршруты. Для одного вызова использовать встроенный стандартный рецепт; собственные рецепты нужны составным действиям.
4. Подключить SDK, постоянное сохранение результатов, acknowledgement, удаление содержимого и обработку событий.
5. Подключить начисления из платёжного сервиса либо административного бюджета.
6. Пройти приёмочные сценарии повторов, исчерпания средств, неизвестного исхода и восстановления.

Профили и рецепты экспортируются как версионируемая конфигурация без секретов. Развёртывание другого приложения не должно требовать изменения кода ядра.

## Модульная админка

`apps/admin` является сборкой интерфейса установки. Переиспользуемый макет находится в `packages/admin-shell`, страницы и серверный адаптер UAI — в `packages/admin-module`. Продукт регистрирует свои страницы и owner-only обработчики в сборке, не изменяя финансовое ядро. Контракт подключения и ограничения описаны в [единой модульной админке](MODULAR_ADMIN.md).

Пользовательский frontend продукта разворачивается отдельно. Общая административная сборка подключает исходный UAI из одного репозитория через Git submodule; свои страницы настроек и платежей продукт хранит вне UAI. Общие исправления принимаются в UAI, затем продукты обновляют зафиксированный commit после проверки совместимости.

## Реализованный распределённый runtime

Локальная установка использует BullMQ для доставки request IDs, PostgreSQL для разрешений выполнения и финансов, Redis для окон квот и S3 для файлов. API, scheduler, generation, observation и maintenance запускаются отдельными процессами. Backend, generation и purpose закрепляются в durable dispatch; завершённый job в Redis не является источником истины о результате или списании.

Правила квот проверяются всем набором в одной финальной Lua-команде. Большая история подготавливается короткими проходами без выдачи permits. Concurrency провайдерской группы хранится в PostgreSQL вместе с защитными удержаниями неизвестных исходов. Session locks групп сериализуют подготовку допуска, но SQL-транзакции не удерживаются на время Redis или HTTP. После Redis все группы подтверждаются одной короткой SQL-транзакцией с повторной проверкой fence, deadline, отмены и конфигурации. Это конкретизация реализации: ранний план описывал concurrency вместе с окнами внутри Lua; фактический источник concurrency остаётся долговечным PostgreSQL. Обе стороны разрешения обязательны перед submission intent.

Состояние внедрения и пределы доказательства перечислены в текущей матрице и аудите завершения. Работа нескольких контейнеров одного Docker host не объявляется проверкой независимых VPS.
